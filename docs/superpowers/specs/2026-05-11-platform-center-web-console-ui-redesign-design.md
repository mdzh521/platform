# Platform Center Web Console UI 重做设计

## 1. 背景

`platform-center/apps/web-console` 当前已经具备较完整的功能入口，但界面表达仍然停留在“功能原型已拼起来”的阶段：

- 顶层导航、模块标题和页面编排还不够像正式产品壳层
- 首页更偏说明页，尚未成为真实的工作起点
- 交付、集群、机器、系统治理四类能力虽然已分模块，但主次关系不够清晰
- 页面里存在较多说明性大段文案、堆叠式面板和近似 demo 的视觉表达
- 主用户是平台/运维工程师，但当前结构没有明显把高频操作域放在最前面

这次工作不是简单换肤，而是一次以信息架构、产品壳层和页面节奏为核心的 UI 重做。目标是在尽量保持现有功能逻辑可用的前提下，把控制台升级为更正式、可连续使用的 SaaS 运维工作台。

## 2. 用户与目标

### 2.1 主要用户

主要用户是混合角色中的平台/运维工程师。系统治理类能力仍然重要，但优先级低于以下高频工作：

- 云交付与基础网络编排
- 集群范围内的资源浏览、排障和操作
- 机器资产、凭据、会话和终端访问

### 2.2 产品目标

本次 UI 重做需要同时达成以下目标：

1. 保留运维控制感，但整体更像正式 SaaS 控制台，而不是监控大盘或临时后台
2. 首页进入后先看到全局状态，再进入具体工作域
3. 将高频操作域前置，将治理域后置
4. 统一一级页面的视觉骨架、导航结构和操作节奏
5. 尽量不打断现有数据加载、事件绑定和业务动作逻辑

## 3. 设计原则

### 3.1 视觉气质

采用“轻指挥台”方向：

- 保留状态感、专业感和控制面属性
- 弱化大屏大盘式监控观感
- 提高留白、分区、层级和节奏控制
- 让颜色更多承担状态与引导职责，而不是全面铺满页面

### 3.2 信息架构原则

- 顶层导航以用户任务域组织，而不是以后台管理栏目组织
- 页面先建立上下文，再展开操作内容
- 治理能力收纳为独立低频域，避免压过高频操作域
- 尽量保持真实领域语义，避免为了“更 SaaS”而做过度抽象

### 3.3 实施原则

- 优先重做公共壳层、一级模块骨架和高感知页面
- 深层详情页先接入新视觉系统，不在本轮追求全部重写
- 优先改 DOM 结构、文案层次和样式系统，尽量少动业务流程

## 4. 顶层信息架构

顶层导航重组为以下 5 个一级入口：

1. `总览`
2. `交付网络`
3. `集群工作台`
4. `机器工作台`
5. `系统治理`

映射关系如下：

- 现有 `overview` 保留为 `总览`
- 现有 `cloud` 重命名并重排为 `交付网络`
- 现有 `business` 重命名并重排为 `集群工作台`
- 现有 `machine` 重命名并重排为 `机器工作台`
- 现有 `system` 重命名并后置为 `系统治理`

这一结构的意图是：

- 保留现有真实任务域，避免引入额外抽象层
- 明确区分高频操作域与低频治理域
- 让导航第一眼就符合平台/运维工程师的日常工作顺序

## 5. 页面骨架设计

### 5.1 全局产品壳

全局壳层改造成稳定的一体化产品框架，包含：

- 品牌区
- 当前一级模块标题与上下文副标题
- 用户与权限信息区
- 一级导航区
- 页面主体容器

现有 topbar 和 top tabs 不再表现为“临时切页按钮”，而是重做为统一产品主导航。品牌、导航、用户信息和模块标题形成更清晰的上下级关系。

### 5.2 一级页面通用节奏

所有一级模块页面统一为三段式节奏：

1. 标题区
2. 指标区
3. 工作区

其中：

- 标题区负责建立当前页面的任务边界、上下文和高价值动作
- 指标区负责快速传达状态、规模、异常或近期变化
- 工作区负责承接表格、筛选器、详情钻取和高频操作

这样页面进入时先建立认知，再让用户执行操作，而不是直接落进按钮与表格堆里。

## 6. 总览页设计

`总览` 将成为新的默认工作起点，不再承担大量介绍性文案。结构调整为：

1. 顶部平台级状态 Hero
2. 全局关键指标卡
3. 三个主工作域入口卡
4. 最近任务 / 最近会话 / 待处理事项区

### 6.1 Hero 角色

Hero 需要传达：

- 当前平台整体健康与运行语境
- 当前迭代关注点或关键提醒
- 进入主工作域的直接动作

但 Hero 的文案需要比现状更短，避免首屏被说明文字占据。

### 6.2 三大工作域入口

首页必须突出以下三个主工作域：

- 交付网络
- 集群工作台
- 机器工作台

每张入口卡应同时提供：

- 域级摘要
- 当前规模或状态
- 直接进入动作

### 6.3 近期活动区

首页底部需要提供“继续工作”的线索，优先展示：

- 最近任务
- 最近会话
- 待处理异常、失败任务或需关注项

这样首页从“介绍页”升级为“进入工作状态的起点页”。

## 7. 各一级模块的重做方向

### 7.1 交付网络

`交付网络` 由现有 `cloud` 页面重组而来，定位为“交付上下文 + Foundation Network + 交付对象 + 执行结果”的连续工作台。

页面应强化以下认知：

- 云账号是上下文，不是孤立资源
- Foundation Network 是底座
- 服务器 / Bastion / Cluster 等交付对象从底座发起
- 任务状态和资源结果需要在同一视角中连续查看

视觉与布局上，这一页更偏流程和编排感，强调阶段关系与对象依附关系。

### 7.2 集群工作台

`集群工作台` 由现有 `business` 页面重组而来，定位为“从集群范围选择到资源与排障操作”的连续工作台。

页面需要优先表达：

- 当前所选集群范围
- 命名空间 / 工作负载 / 资源三层结构
- 详情钻取与操作入口

视觉上应更像资源操作台，而不是分散的管理页集合。

### 7.3 机器工作台

`机器工作台` 由现有 `machine` 页面重组而来，定位为“资产、接入、凭据、会话、终端”的统一连接工作区。

页面需要优先表达：

- 当前机器资产规模与在线状态
- 资产列表与接入能力的关系
- 会话、凭据和终端作为持续工作上下文的组成部分

视觉上应体现“进入连接工作”的语义，而不只是展示资产表格。

### 7.4 系统治理

`系统治理` 由现有 `system` 页面重组而来，定位为低频治理域。

这里继续承载：

- 用户管理
- 角色与绑定
- 身份源
- 系统设置

但在视觉上应比前三个主工作域更克制，减少在整个平台中的主导感，以符合实际优先级。

## 8. 视觉系统调整

### 8.1 总体方向

现有样式中的玻璃感、悬浮感和较强背景渐变需要收敛。新的视觉系统应：

- 保留品牌识别与少量状态色
- 使用更稳的面板边界、卡片层级和内容密度
- 强化标题、指标、筛选条、数据区的层次差异
- 让页面看起来更接近正式企业控制台

### 8.2 组件层面的调整

优先统一以下公共组件：

- 一级导航
- 页面标题区
- 指标卡
- 按钮系统
- 状态标签
- 表格外壳
- 筛选条
- 面板 / 子面板
- 空态与提示块
- 抽屉与模态框

### 8.3 文案层级

中文文案需要从“说明书式长文案”调整为更产品化的表达：

- 标题更短、更像模块名
- 副标题只承担上下文说明
- 面板内长段说明压缩为 1 到 2 句
- 动作文案优先直接表达结果或目标

## 9. 本轮实施范围

本轮仅覆盖以下范围：

1. 重做登录页与全局产品壳
2. 重做总览页
3. 重排并改造四个一级模块的首屏架构
4. 建立公共视觉系统与样式基础件
5. 让深层页面、抽屉和弹窗先接入新的视觉语汇

本轮明确不做：

- 不一次性重写全部深层详情页交互
- 不大规模重写现有业务数据结构或接口组织
- 不在本轮引入新的前端框架或路由体系
- 不为了视觉重做而打断现有模块可用性

## 10. 风险与约束

### 10.1 风险

- `index.html` 当前承载大量结构性 DOM，一级导航重排可能牵动多个查询选择器
- 公共样式改动会影响深层页面，需要控制回归范围
- 现有各域页面内部结构差异较大，统一视觉骨架时要避免把不同工作域做成同一张模板

### 10.2 约束

- 现有数据加载、事件绑定和业务动作逻辑尽量保持不变
- 现有页面 ID、关键 DOM 挂载点和脚本入口需要在必要时兼容保留
- 重构应先提升首屏质量和全局观感，再逐步深入细节页

## 11. 验收标准

本轮完成后，应满足以下标准：

1. 首页能够作为真实默认工作起点使用
2. 顶层导航清楚区分主工作域与治理域
3. 四个一级模块首屏拥有统一但不雷同的产品骨架
4. 整体视觉气质从“原型后台”升级为“正式 SaaS 运维控制台”
5. 现有主要功能入口仍可达，且不出现明显的导航或结构性回归
